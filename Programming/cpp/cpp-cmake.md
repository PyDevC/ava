# CMake beyond the basics

CMake is the build system of every C++ project you'll touch (LLVM/MLIR, PyTorch, ROCm). This note is the *model* behind [[Compilers/MLIR/CMake_Guide]] — targets, options, generators — so you can read and extend existing CMake instead of fearing it.

## The mental model

- **CMake = two phases**: configure (read `CMakeLists.txt`, compute what to build → generates `build.ninja`/`Makefile`) then build (`cmake --build`). Changing a `.cpp` = build only; changing `CMakeLists.txt` = reconfigure.
- **The unit is a *target***: `add_library(foo ...)`, `add_executable(bar ...)`, `add_library(baz INTERFACE ...)` (header-only). Everything else (`target_link_libraries`, `target_include_directories`, `target_compile_options`) *attaches properties to a target*. Modern CMake = `target_*` functions, not global variables.
- **The generator**: Ninja (fast, parallel) is the default choice (`-G Ninja`); Makefiles for legacy. Configure: `cmake -G Ninja -B build -DCMAKE_BUILD_TYPE=Release`.

## The common pattern

```cmake
cmake_minimum_required(VERSION 3.20)
project(myproj LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)

add_library(mylib src/foo.cpp src/bar.cpp)
target_include_directories(mylib PUBLIC include)
target_link_libraries(mylib PUBLIC fmt::fmt)   # dependency via find_package

find_package(MLIR REQUIRED)                    # see MLIR CMake_Guide
add_executable(mytool src/main.cpp)
target_link_libraries(mytool PRIVATE mylib)
```

- **`find_package(MLIR)`** — the interface to *other projects'* build systems (their exported targets). The package must have been built+installed with CMake *and* export its targets (see [[Compilers/MLIR/CMake_Guide]]).
- **Build types**: `Debug` (asserts), `Release` (`-O2`), `RelWithDebInfo` (release + symbols — the default for "fast but debuggable"). Sanitizers: add flags yourself (see [[cpp-debugging]]).

## The pain points (and fixes)

- **"No rule to make target" / include not found**: the target isn't linked (`target_link_libraries`) or the include dir isn't `PUBLIC`. Check `cmake --build` output for the actual missing include.
- **Reconfigure storms**: cache (`CMakeCache.txt`) persists options; delete `build/` for a clean slate. `cmake -LAH` lists cache options.
- **Generated files** (MLIR `mlir-tblgen` outputs): they're build artifacts generated by a custom command — edit the `.td`, *not* the generated `.inc` (see [[Compilers/MLIR/TableGen]]).
- **Presets** (`CMakePresets.json`) — the modern way to encode "how to configure this repo" (`cmake --preset=dev`). LLVM/PyTorch use them.

## The LLVM/MLIR flavor

LLVM builds CMake *itself* (add_subdirectory of `llvm/`), so MLIR is a subproject of LLVM's CMake — that's why you need LLVM's build (or a release) before your MLIR project (see [[Compilers/MLIR/CMake_Guide]]). PyTorch similarly is one huge CMake project (`torch/csrc` + subprojects).
